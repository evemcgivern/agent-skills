## ServiceNow: intake through a catalog item, decisions through an approval workflow

A governance intake form (this method's step 5) maps onto a **Service Catalog** item: a catalog item carries a request form and a **Workflow** field that defines its fulfilment process, including any approval step. Submitting the item creates a **Request** (table `sc_request`), which in turn creates one or more **Requested Items** (`sc_req_item`, referencing the originating **Catalog Item** on `sc_cat_item`); the request-level approval covers everything in the cart, and once that clears, each requested item's own fulfilment work is tracked as **Catalog Tasks** (`sc_task`).

Approval logic is built either in the classic **Workflow Editor** or in **Flow Designer**, using activities such as **Approval - User**, **Approval - Group**, or **Approval - Action**, evaluated against a **Condition** — the mechanism a cost or risk threshold (this method's step 3) would be built on, for example routing to the council only when a requested item's cost exceeds a set figure. Approval records live on table **`sysapproval_approver`**, confirmed by multiple ServiceNow Community and Support sources, and move through states such as Requested, Approved, Rejected, and Canceled — the natural place to attach this method's decision log, alongside workflow activity logs and notifications for each decision. A council's decision log therefore maps onto ServiceNow's own Service Catalog tables end to end: `sc_request` → `sc_req_item` (from `sc_cat_item`) → `sc_task`, with approvals on `sysapproval_approver`. ServiceNow's own documentation confirming the exact field-level distinction within the approval table (for example, between an "Approving" and an "Approval for" field) could not be loaded; the table name itself is confirmed by multiple sources.

## Flexera One: usage, spend, and shadow IT discovery as meeting inputs

Flexera One's SaaS Management product is built to feed exactly the kind of item this method's intake and meeting inputs need: it combines **application usage, license data, and spend insights** to surface waste, and its discovery draws on multiple sources at once — Flexera names financial and expense data, API connectors, a browser extension, and connections to single sign-on (SSO) and Cloud Access Security Broker (CASB) systems — to build a fuller picture than any one source alone, including applications nobody sanctioned. That combined view of usage, spend, and contract data is what Flexera positions as the basis for governance and license-optimization decisions, which is the natural agenda input for this method's cadence step (rather than convening the body with no live item to decide on).

No confirmed Flexera One field, table, or dashboard name exists for a per-application "last reviewed" or "last decided" date that this method's decision log could cite directly; Flexera's documented capability is usage-and-spend-based discovery and optimization recommendations, not a named governance-decision object. The claims above come from Flexera's product and solution marketing pages, which loaded and are cited directly.
