# Ambition

Help the user choose a more valuable outcome. This is an advisory workflow:
invoking it does not authorize implementation, a paid experiment, publication,
or a mission. Do not make it a mandatory gate before already-authorized work,
shrink an existing assignment into a prototype, or expand that assignment.

## Ground the options

Use the named project, idea, or goal. Read the relevant project instructions,
current behavior, roadmap or shelved proposal, and available tools. Inspect only
enough to identify the constraint that previously made the idea unattractive.
If no project can be inferred, ask which project or outcome to consider.
If no historical constraint is documented, label it as an inference from the
current design. Do not invent a prior decision or a change in capability.

Separate three things in your notes and output:

- **Observed:** what the files, working application, or user establish.
- **Assumed:** what would have to be true for the option to pay off.
- **Untested capability:** what the agent or tool has yet to demonstrate here.

Verify changeable claims about external tools or models against current primary
sources. An impressive demo or benchmark is a reason to test a hypothesis, not
evidence that this particular project is now feasible. Name missing access or
data instead of assuming it can be acquired.

## Propose three outcomes

Give three meaningfully different options, each with:

- The concrete result and who would benefit.
- The old constraint being challenged and evidence that it may have changed.
- The hardest remaining uncertainty, likely effort, and material downside.
- A source reference for project facts; label estimates and inferences.

Prefer options that change what the user can accomplish. More generated code,
more agents, or a larger feature list is not by itself a better outcome. Include
spatial, interactive, research, or application workflows only when they serve
the actual project. If fewer than three options are defensible, say so rather
than padding the list.

Recommend one option and explain why it beats the alternatives. It is valid to
recommend leaving the current scope alone when there is no convincing upside.

## Design the decisive experiment

For the recommended option, specify:

1. **Hypothesis:** the uncertain claim the experiment will resolve.
2. **Smallest convincing artifact:** something the user can run, inspect, or use.
3. **Procedure:** concrete inputs, environment, tool or command, and output. If
   a script does not exist, identify creating it as work; do not present an
   invented command as runnable. State the comparison or baseline.
4. **Pass/fail:** observable acceptance criteria, including what would falsify
   the idea. Distinguish functional evidence from subjective user judgment.
5. **Resources:** a proposed time/spend/token ceiling and required access. Honor
   any supplied budget. An estimate or proposed ceiling is not authorization
   to spend, and unknown usage must stay unknown.
6. **Next decision:** what a pass, failure, or inconclusive result would justify.

Do not silently carry out the experiment. When the user authorizes it, use the
existing execution and verification tools. If they also request durable
continuity, hand the selected outcome, constraints, milestones, and acceptance
criteria to the mission skill, if installed; otherwise give a self-contained handoff.

## Deliverable

Keep the result easy to compare: a short context paragraph, an options table,
the recommended experiment, and the decision needed from the user. Preserve
the full intended outcome while making its uncertain assumptions testable.
An optional experiment decision does not pause other authorized work.
